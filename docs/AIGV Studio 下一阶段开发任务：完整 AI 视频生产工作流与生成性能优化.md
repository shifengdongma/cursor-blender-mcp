# 三、第一阶段：实现真实配音与素材管理

## 3.1 第 04 步总体目标

将“配音与素材”页面真正变成音频制作中心。

用户应能够针对每个分镜：

- 编辑旁白。
- 选择真实可用的音色。
- 生成配音。
- 试听配音。
- 重新生成配音。
- 调整语速和音量。
- 选择或上传背景音乐。
- 添加音效。
- 控制各音频片段的起止时间。
- 将结果加入时间线。
- 保存编辑结果。

### 3.2 完善真实 TTS 服务

当前已有：

`backend/providers/tts_provider.py`

以及：

`backend/task_worker.py` 中的 `_execute_tts()`。

请优先复用。

建议设计统一 TTS Provider 接口：

```python
class BaseTTSProvider:
    def list_voices(self):
        ...

    def synthesize(self, text, voice_id, output_path, options=None):
        ...

    def get_capabilities(self):
        ...
```

首期确保 Piper 本地 TTS 可以真实运行。

根据现有实际部署环境检测：

- 是否安装 Piper。
- Piper 可执行文件位置。
- 是否存在真实 `.onnx` 模型。
- 是否具有匹配的模型配置。
- FFprobe 是否可执行。
- 输出 WAV 是否正常。
- 中文配音是否正常。

当前前端存在类似 `vp-001`、`vp-002` 的音色编号，不能直接将这些展示用 ID 当作 Piper 模型路径传递。

需要建立服务端音色注册表，将前端 voice_id 映射到实际合法音色配置。

音色列表由后端返回。

未安装的音色不能显示成可直接生成的真实音色。

### 3.3 可选云端 TTS

为了让中文配音更自然，增加可选云端语音合成方案。

优先考虑：

- 阿里云百炼 Qwen TTS。
- 火山引擎豆包语音。

开发前检查官方最新 API 文档、区域、音色、鉴权和费用要求。

建议首期只选择一个云端 Provider 实现，不要同时接入大量 TTS 服务。

实现时保持：

- 本地 Piper 可用。
- 云端 TTS 可选。
- 可按音色和服务能力切换。
- 不配置云端密钥时不影响本地 TTS。
- API Key 不暴露到浏览器。
- 真实生成失败时返回错误，不生成假音频。

云端语音合成属于可选增强功能，不能阻塞本地完整视频工作流的交付。

### 3.4 改造配音生成方式

当前 `/api/creative/projects/<project_id>/tts` 主要按整个项目创建任务。

需要增加按单个分镜生成或重生成配音的能力。

建议新增或扩展：

```text
POST /api/creative/shots/<shot_id>/tts
GET  /api/creative/tts/voices
```

同时保留原项目级 TTS 接口用于批量生成。

请求参数至少支持：

```json
{
  "provider": "piper",
  "voice_id": "configured_voice_id",
  "text": "需要生成的旁白内容",
  "speech_rate": 1.0,
  "volume": 1.0
}
```

后端必须检查 Provider 是否支持这些参数。

如果某模型不支持语速，则可以通过有质量保证的音频变速后处理实现，但不能静默忽略。

音量可以通过 FFmpeg 处理实现。

输出需要记录：

- 任务 ID
- 所属用户
- 所属项目
- 分镜 ID
- TTS Provider
- 真实音色 ID
- 旁白文本
- 语速、音量
- 音频路径
- 音频时长
- 生成时间

每次重新生成配音创建独立素材记录。

旧音频不应直接覆盖，便于用户恢复历史版本。

### 3.5 修复字幕与配音关联

当前 `_execute_tts()` 中 `srt_path` 被用于保存 WAV 路径，需要改正。

明确区分：

- `audio_asset_id`：配音素材 ID。
- `subtitle_asset_id` 或字幕文件路径：真实字幕文件。
- `dialogue`：旁白原文。

字幕时间需要与分镜开始时间和实际配音时长对应。

首期支持基于句子或分镜的字幕块生成，不要求复杂的语音强制对齐。

如果后续需要逐字字幕，可以单独引入语音时间戳或强制对齐工具。

**不能只根据文本长度假装得到精确语音时间戳。**

### 3.6 配音结果预览

在第 04 步的每个分镜增加：

- 配音状态。
- 音色名称。
- 真实时长。
- HTML Audio 播放器。
- 下载按钮。
- 重新生成按钮。
- 使用当前配音按钮。

用户切换项目、刷新页面或者重新登录后仍应看到已保存配音。

对于没有旁白的分镜，允许设置无配音，而不是强制生成空白语音。

### 3.7 背景音乐真实化

当前背景音乐选择主要来自前端写死的音乐类型。

改造为实际音频素材库。

首期支持两种来源：

**用户上传音乐**

支持上传经验证的 MP3、WAV、AAC、M4A 等常见格式。

服务端检查实际编码格式、大小、时长和安全性。

**系统预设音乐**

仅使用项目已实际拥有合法使用权的音频素材。

如果仓库没有实际授权音乐文件，不允许伪造音乐资源。

可以暂时让系统预设音乐库为空，保证用户上传音乐的功能先可用。

后台记录素材的所有者、名称、类型、时长、音量默认值、文件路径和授权信息。

第 04 步支持：

- 选择已上传音乐。
- 在线试听。
- 将音乐添加到时间线。
- 设置音量。
- 设置开始时间。
- 设置结束时间。
- 循环或裁切。
- 删除音乐片段。

音乐必须真正参与最终合成。

### 3.8 音效真实化

类似背景音乐，音效应当引用真实音频资产。

支持：

- 上传短音效。
- 从已有音效素材中选择。
- 预览播放。
- 添加到指定时间点。
- 修改音量。
- 修改持续时间。
- 删除音效。

当前演示卡片上的名称可以保留为分类或模板，但只有存在真实音频文件的选项才允许点击试听和使用。

### 3.9 音频安全

必须验证用户对音频素材的所有权。

不得接受任意服务器文件路径。

处理上传文件时使用受控文件目录，并设置容量限制。

禁止前端传入任意 URL 让 FFmpeg 访问内网、云元数据地址或本地文件。

# 四、第二阶段：实现真实多轨时间线

## 4.1 总体目标

将当前“视频轨、配音轨、音乐轨、音效轨、字幕轨”改造成真正参与后端合成的视频编辑时间线。

首期实现个人能够维护的轻量时间线编辑器，不要求达到 Premiere、DaVinci Resolve 等专业软件的完整复杂度。

但必须保证编辑结果可以真实合成。

## 4.2 复用现有数据库

项目已有：

- `timeline_tracks`
- `timeline_clips`
- `TimelineTrack`
- `TimelineClip`

以及：

```text
GET /api/creative/projects/<project_id>/timeline
PUT /api/creative/projects/<project_id>/timeline
```

优先复用现有表结构，不要重新建立一套完全独立的时间线数据库。

根据需要增加字段：

- asset_id
- shot_id
- start_time
- duration_s
- trim_in
- trim_out
- volume
- muted
- source_audio_enabled
- fade_in
- fade_out
- subtitle_text
- timeline_version

已有 `properties` JSON 可以承载不需要建立独立数据库字段的配置。

所有参数都必须经过后端验证。

## 4.3 自动创建初始时间线

当用户完成第 03 步并首次进入第 04 步时：

1. 从数据库读取分镜。
2. 按 `sequence_no` 排序。
3. 读取每个分镜已生成的视频资产。
4. 检查视频是否真实存在。
5. 使用 FFprobe 获取视频实际时长。
6. 自动生成视频轨。
7. 如果分镜已有配音，创建对应配音轨片段。
8. 如果分镜已有字幕，创建对应字幕块。

必须使用真实文件时长，不要将演示中的 `60 秒` 作为默认项目总时长。

初始化应具备幂等性。

如果已经存在用户编辑过的时间线，不允许再次进入页面时将其覆盖。

## 4.4 实现时间线编辑

基础编辑要求：

- 拖动片段改变位置。
- 选择片段。
- 调整片段起点和终点。
- 删除片段。
- 静音片段。
- 调整音量。
- 调整片段顺序。
- 预览指定素材。
- 保存时间线。
- 加载已保存时间线。

对于视频轨，首期可以限制为单条主视频轨，避免处理复杂的视频重叠合成。

允许音频轨存在重叠，用于背景音乐与音效混合。

支持适度吸附到分镜边界或时间刻度，提高编辑体验。

不必首期开发复杂关键帧动画系统。

## 4.5 前后端数据同步

当前 `state.trackData` 主要用于前端展示。

请将它改造成从后端时间线 API 读取和保存的编辑状态。

建议：

- 前端使用统一时间线数据结构。
- 页面加载时读取服务端。
- 编辑后以防抖机制自动保存。
- 提供明确保存状态。
- 项目切换前保存未提交数据。
- 处理并发修改冲突。
- 页面刷新后恢复。
- 保存失败时不显示成功。

特别注意，当前 PUT 时间线接口采取先删除再插入的方式，需要加入数据库事务和输入校验，避免中途失败导致时间线丢失。

应验证所有 clip 中的 asset_id、shot_id 均属于当前用户有权访问的项目或素材。

## 4.6 时间线与后端视频合成一致

时间线必须成为视频合成的实际输入。

最终 FFmpeg 合成顺序不能再直接依赖简单的分镜数组。

要求从数据库读取已保存的时间线快照，确定：

- 主视频片段顺序。
- 各片段实际裁剪区间。
- 配音开始时间。
- 背景音乐起止。
- 音效播放位置。
- 音量与静音设置。
- 字幕起止时间。

创建合成任务时保存时间线快照，避免用户在合成过程中修改时间线导致结果不一致。

# 五、第三阶段：将第 05 步改造为真实单镜头调试

## 5.1 总体目标

当前第 05 步是可选调试流程。

保持其可选性质，但实现真正针对视频素材的精修能力。

用户可以：

- 选择需要调整的分镜视频。
- 查看原始视频。
- 修改实际可支持的画面参数。
- 预览调整效果。
- 提交真实 FFmpeg 精修任务。
- 查看精修完成的视频。
- 选择是否将精修版本应用到最终成片。

## 5.2 修复原始画面与精修画面对比

目前 `renderModule5()` 使用渐变占位画面。

请替换为真实视频播放器。

建议采用左右对比布局：

**左侧：原始视频**

播放选中分镜的真实视频。

**右侧：精修预览**

使用相同视频源，前端 CSS 滤镜做即时视觉预览。

两个播放器保持播放位置、暂停状态尽可能一致。

需要明确提示：CSS 是快速预览，实际导出由后端 FFmpeg 完成。

不能将 CSS 预览误称为已生成文件。

## 5.3 真实支持的滤镜

优先实现：

- 亮度。
- 对比度。
- 饱和度。
- 色调。
- 模糊。
- 锐化。
- 简单曝光调整。
- 视频裁切。
- 分辨率调整。
- 帧率转换。

如果部分参数无法稳定映射到 FFmpeg，应禁用或删除对应控件，不能只改变浏览器画面却不影响实际导出。

明确参数单位与范围，做好输入校验和 FFmpeg 参数转义。

优先使用：

`backend/media_service.py` 中的 `apply_filter_chain()`。

禁止将前端原始字符串直接拼接进 Shell 命令。

## 5.4 单镜头精修任务

复用：

```text
POST /api/creative/projects/<project_id>/refine
```

建议补充或明确传参：

```json
{
  "shot_id": "real-shot-id",
  "input_asset_id": "real-video-asset-id",
  "filters": {
    "brightness": 0.05,
    "contrast": 1.1,
    "saturation": 1.08
  }
}
```

后端必须确认该素材有权使用且属于目标项目的可编辑视频素材。

精修成功后：

- 创建新的真实视频资产。
- 保留原始视频。
- 保存滤镜参数。
- 将结果关联分镜。
- 支持预览。
- 支持下载。
- 允许选择“使用精修版”或“恢复原始版”。

不能直接覆盖原始 AI 生成视频。

可以用版本关系或独立分镜选择表记录当前使用的版本。

## 5.5 修复当前精修输入选择问题

当前 `handleStartAiBatch()` 会从分镜列表中寻找第一个可用 `video_asset_id`。

这不符合“单镜头调试”的语义。

应改成针对用户当前选中的分镜执行。

没有选中的分镜时必须提示用户选择。

成功生成的新精修资产必须明确绑定到对应分镜，最终合成时使用用户选择的版本。

## 5.6 AI 精修功能的边界

当前界面中部分“AI 批处理”属于演示功能。

本阶段不要为实现高级 AI 精修而重新引入一整套视频扩散模型。

先确保 FFmpeg 的确定性处理功能真实可用。

如果保留“AI 增强”“AI 超分”等选项，必须存在实际可用模型、真实 API 或本地处理工具。

否则将其标识为未接入，不允许返回模拟成功。

# 六、第四阶段：实现完整 MP4 成片合成与导出

## 6.1 核心目标

这是全流程能否真正交付的关键。

当前第 06 步只支持导出 ZIP 素材包。

本次必须新增：

**导出最终视频（MP4）**

保留已有：

**导出项目素材包（ZIP）**

两个功能可以并存。

## 6.2 真实视频合成流程

根据已保存时间线，执行：

```text
读取项目与时间线
        ↓
校验素材及权限
        ↓
读取视频和音频元数据
        ↓
处理视频片段顺序与裁剪
        ↓
统一分辨率、帧率与编码
        ↓
拼接完整视频轨
        ↓
合并配音、背景音乐和音效
        ↓
生成或加载字幕
        ↓
字幕封装或烧录
        ↓
生成最终 MP4
        ↓
FFprobe 验证
        ↓
保存视频素材
        ↓
前端预览与下载
```

不得只返回 FFmpeg 执行成功消息。

必须检查最终文件存在、大小合理、能够正常解码、具有正确的媒体轨道。

## 6.3 修复 `_execute_compose()`

重点检查：

`backend/task_worker.py`

`backend/media_service.py`

当前存在视频合成和音频合成分离的问题。

必须将最终音频真正映射到 MP4 文件中。

建议在 `MediaService` 中增加基于时间线的合成方法，例如：

```python
def compose_timeline(
    self,
    timeline,
    output_path,
    export_settings,
):
    ...
```

该方法负责将不同来源的媒体片段统一构建为真实 FFmpeg 滤镜图。

不要求必须使用上述函数名，但需要有明确的媒体合成服务入口。

### 视频轨要求

- 按真实时间线顺序拼接。
- 支持 `trim_in` 和 `trim_out`。
- 统一宽高、像素格式、帧率和时间基。
- 保留正确画面比例。
- 缺少必要视频时给出明确错误。
- 如果允许静态图片作为替代镜头，必须真实生成静态视频片段。
- 不要产生大量不必要的中间编码文件。

### 配音轨要求

- 按各分镜实际时间位置插入配音。
- 无配音段落保持安静。
- 支持音量调整。
- 避免配音之间非预期的覆盖。
- 旁白长度超过分镜时给出明确处理策略。

默认策略建议：

若配音超出镜头长度，提示用户调整语速、裁切或延长镜头；不要静默截断重要旁白。

### 背景音乐要求

- 支持音乐覆盖整个视频。
- 支持裁切和循环。
- 支持整体音量调整。
- 支持淡入淡出。
- 与配音同时播放。

有配音时可选自动降低背景音乐音量。

可使用 FFmpeg 的 `volume`、`amix`、`adelay`、`atrim`、`afade`、`sidechaincompress` 等功能。

实际使用哪些滤镜需根据素材采样率和编码情况确定。

### 音效要求

- 支持按时间插入。
- 支持多个音效同时存在。
- 支持音量调整。
- 不影响整体视频时长。
- 超出视频时长的部分合理裁切。

### 原视频声音

Seedance 等视频模型可能已经生成音频。

需要在时间线中区分：

- AI 视频自带声音。
- TTS 旁白。
- 背景音乐。
- 独立音效。

默认不要简单全部叠加，否则可能造成声音重复和音量失控。

建议增加“保留原视频声音”开关，并能够设置原视频音量。

最终输出应防止音量叠加削波，可按实际需要加入响度调整或限幅。

## 6.4 字幕合成

至少支持：

- 生成真实 SRT 文件。
- 根据时间线位置保存字幕时间。
- 字幕文本编辑。
- 字幕开关。
- 下载字幕。
- 可选将字幕烧录到视频。

字幕需要考虑中文字体兼容。

如果服务器缺少字体，给出明确依赖提示。

对不同视频输出模式：

- 不烧录字幕时，可以提供独立 SRT。
- 烧录字幕时，需真实执行 FFmpeg 字幕处理。

不能只在浏览器预览时显示字幕，而导出视频没有字幕。

## 6.5 最终视频格式

首期优先实现稳定的：

- MP4 容器。
- H.264 视频编码。
- AAC 音频编码。
- 720p / 1080p 输出。
- 24 / 30 FPS。
- 合理的码率控制。

如果当前服务器资源足够，再考虑增加更高分辨率。

用户选择的输出分辨率不得被视为源素材已经具备相同原生画质。

例如将 720p 放大到 4K 不能宣传为原生 4K AI 视频。

不要求首期实现 VR 360°、立体视频或专业多声道格式。

如现有平台卡片包含这些能力，需要将未支持项禁用或明确标注。

## 6.6 最终视频页面

第 06 步增加：

- 导出参数。
- 生成最终视频按钮。
- 真实任务进度。
- 最终视频播放器。
- 输出时长。
- 分辨率。
- 帧率。
- 文件大小。
- 下载 MP4。
- 下载 ZIP 素材包。
- 重新合成。

播放及下载地址必须通过受保护的素材 API 提供。

项目完成后，用户再次进入第 06 步应能查看已有成片，而不需要重新执行昂贵的 API 生成操作。

## 6.7 复用 ZIP 导出

保留现有 `_execute_export()`。

但需要完善导出内容：

```text
项目导出包
├── final/
│   └── final_video.mp4
├── videos/
│   ├── shot_001.mp4
│   ├── shot_002.mp4
│   └── ...
├── audio/
│   ├── narration/
│   ├── music/
│   └── effects/
├── images/
├── subtitles/
│   └── subtitles.srt
├── manifest.json
└── project.json
```

只打包项目实际存在的文件。

必须校验文件属于当前项目，不能读取其他用户私有素材。

Manifest 应真实反映输出文件、模型信息和生成参数。

## 6.8 导出任务安全与可靠性

所有输出使用独立任务 ID 生成路径，避免同一项目并发导出互相覆盖。

FFmpeg 执行失败时保留错误记录。

临时文件在任务成功或失败后按策略清理。

输出文件必须经过实际探测。

对视频总时长、输入素材数量、分辨率和磁盘空间设置合理上限。

# 七、第五阶段：AI 图片和视频生成性能分析

本阶段不允许先盲目修改线程数或 API 超时参数。

必须先完成性能监测。

## 7.1 建立真实耗时记录

重点检查：

- `backend/generation_service.py`
- `backend/generation_worker.py`
- `backend/task_service.py`
- `backend/providers/volcengine_image.py`
- `backend/providers/volcengine_video.py`
- `backend/providers/llm_provider.py`
- `backend/media_fetcher.py`
- `web/creative-studio.js`

为每个生成任务记录必要时间点：

```text
created_at
claimed_at
provider_request_started_at
provider_request_finished_at
provider_job_created_at
provider_finished_at
download_started_at
download_finished_at
persist_finished_at
completed_at
```

根据模型类型，有些时间点可能不存在，应允许为 null。

使用单调时钟测量单进程执行耗时，使用 UTC 时间戳记录跨进程事件。

统计：

- 队列等待时间。
- API 提交耗时。
- Provider 排队及运行耗时。
- 结果下载耗时。
- 本地数据持久化耗时。
- 任务总耗时。
- 前端结果可见延迟。

如 Provider 不返回实际推理开始时间，不得将“提交至完成”全部标记为纯模型推理时间。

## 7.2 提供性能诊断输出

建议新增一个简单性能诊断能力：

```text
GET /api/generation/tasks/<task_id>/timing
```

或者在已有任务详情中提供时间统计字段。

普通用户只能查看自己的任务。

管理员可以查看整体生成性能聚合数据。

统计报告至少支持按以下维度区分：

- 图片或视频。
- Provider。
- 模型 ID。
- 是否使用参考图。
- 分辨率。
- 视频时长。
- 成功或失败。
- 等待与下载耗时。

禁止记录 API Key、认证头、完整用户隐私内容和未脱敏的敏感响应。

## 7.3 排查 Worker 并发瓶颈

当前 `GENERATION_WORKER_CONCURRENCY` 默认值为 1。

需要分析以下影响：

- 同步图片生成是否长期占用 Worker。
- 视频状态轮询是否影响新任务提交。
- 结果下载是否阻塞其他任务处理。
- 多用户任务是否可能互相排队。
- SQLite 是否存在较长写锁等待。

建议在确认服务器资源后，先测试适度增加 Worker 并发，例如 2 或 3，而不是直接开到几十个。

同时必须检查 Provider 并发额度与用户每日调用限制。

需要评估是否将：

- 任务提交。
- 异步状态轮询。
- 结果下载和持久化。

拆分为不同的执行队列或线程池。

但首期应优先在现有 GenerationWorker 基础上作最小调整，保证 SQLite 租约机制和幂等性不被破坏。

## 7.4 避免轮询阻塞提交

当前 Worker `run_once()` 优先处理可轮询任务。

需要检查大量运行中视频任务时，待提交的新图片或视频任务是否被持续推迟。

如果存在该问题，采用公平调度方式：

- 提交任务保留一定处理能力。
- 状态查询不得无限占用队列。
- 下载完成任务可按优先级处理。
- 不超过 Provider 限流额度。

不能为追求低延迟使轮询请求无限增加。

## 7.5 优化 Provider HTTP 请求

当前 Provider 主要使用 Python requests。

检查是否存在：

- 每次请求都新建 TCP/TLS 连接。
- 不必要的重复模型查询。
- 过长的请求超时。
- 不合理的失败重试。
- 大型 Base64 参考图重复编码。
- 多次上传同一张图片。

可以评估复用 `requests.Session` 连接池，减少重复建连成本。

注意 Session 的线程安全和生命周期，避免多个线程共享可变认证头导致密钥串用。

HTTP 超时应区分连接超时与读取超时。

不要简单将 180 秒改成 10 秒，否则可能产生大量状态不确定、重复提交和计费问题。

需要保留现有异常分类及 `needs_review` 安全机制。

## 7.6 优化参考图片传输

重点检查：

`generation_service._reference_data_urls()`

以及 Provider 创建视频任务时的 `reference_image_urls`。

分析参考图是否经过本地读取、Base64 编码并直接嵌入请求。

如果存在明显传输开销，可以考虑：

- 使用服务商支持的远程图片 URL。
- 使用经过认证、时效受控的对象存储 URL。
- 在符合模型要求和用户选择的质量约束下压缩参考图。
- 避免重复转换同一图片。
- 使用可信缓存。

如果使用远程 URL，必须检查服务商能否实际访问，并解决鉴权和临时链接有效期问题。

不能通过公开所有用户素材来实现传图加速。

## 7.7 优化图片生成

针对实际模型能力，考虑增加“快速预览”模式。

快速预览可使用：

- 更低的图片尺寸。
- 更适合低延迟的已开通模型。
- 较少的生成数量。

只有用户选择快速预览时才使用这些参数。

正式生成保留用户原本选择的模型和质量档位。

禁止后台偷偷降低图像质量而不提示。

要特别区分：

- 模型计算时间。
- 网络往返时间。
- 图片下载时间。
- 浏览器显示时间。

优化指标需分别统计。

## 7.8 优化视频生成

针对 Seedance 等视频模型，提供合理的生成档位：

**快速预览**

使用模型实际支持的低分辨率、较短时长或 Draft 模式。

**正式生成**

使用用户选择的完整模型能力。

Draft 模式、低分辨率与不同服务等级可能涉及不同模型支持条件及计费方式，必须按最新官方文档实现。

不能把降低分辨率后的结果当作用户请求的正式高清成片。

对生成过程：

- 提交后尽快返回本地任务 ID。
- 前端无需持续等待单个 HTTP 请求。
- 在后台持续管理 Provider 任务。
- 页面刷新后可恢复。
- 完成后及时下载结果。
- 保存结果供后续配音和合成使用。

如使用 Webhook，需要验证来源与任务关联，设计幂等回调处理；仍须保留轮询恢复机制。

## 7.9 减少生成成功后的等待

当前视频完成后还需要下载远程结果。

应检查：

- 文件大小。
- 下载网络吞吐。
- DNS 和连接耗时。
- 服务器出口带宽。
- 磁盘写入速度。
- 文件哈希校验耗时。

如果结果文件体积较大，可考虑独立下载执行池，避免占用任务提交 Worker。

不得为了加速而关闭当前 SSRF、文件类型和大小验证。

可以在 Provider 已成功但本地尚未转存完成时显示：

“模型生成完成，正在保存视频”。

避免用户误认为模型仍在生成。

## 7.10 前端性能优化

当前 `pollTask()` 每 2 秒查询一次任务状态。

视频生成过程中可能频繁重新渲染模块。

请检查是否引起：

- 页面闪烁。
- 表单状态丢失。
- 视频播放器重建。
- 图片重复加载。
- 多次重复请求。
- 长时间任务恢复异常。

优化方式：

- 仅更新任务状态和时间信息。
- 状态未变化时避免完整重建模块。
- 任务结束后再更新结果卡片。
- 页面不可见时适当降低查询频率。
- 切换项目或页面时取消无效轮询。
- 使用 `AbortController` 或对应机制控制旧请求。
- 保证页面刷新后能够恢复运行中任务。

如采用 SSE，应保留兼容性良好的普通轮询方案。

## 7.11 LLM 创意分析优化

检查：

`backend/providers/llm_provider.py`

以及：

`backend/task_worker.py` 中的分镜生成流程。

重点分析：

- 是否一次请求生成过多分镜。
- Prompt 是否过长。
- 模型输出 Token 是否过多。
- 是否存在无意义重复调用。
- JSON 解析失败是否导致重新生成。
- LLM 分镜任务是否被其他旧版任务堵塞。

可采用：

- 精简系统 Prompt。
- 明确结构化输出。
- 根据用户选择控制分镜数量。
- 限制不必要的描述字段。
- 在模型支持时使用结构化 JSON 输出。
- 为相同请求设置受控缓存。
- 增加提交和响应耗时监测。

不能为了提速而删除用户实际需要的分镜描述、镜头设计和 Prompt 结果。

## 7.12 单独优化后期制作性能

TTS、FFmpeg 合成、精修和 ZIP 导出属于本地媒体任务，与外部 AI 推理任务不同。

需要单独优化：

- Piper 模型是否每个分镜重复启动。
- 是否可以复用已生成配音。
- FFmpeg 是否存在重复转码。
- 视频拼接是否可以在条件允许时使用流复制。
- 编码 preset 是否适合实际服务器 CPU。
- 是否同时执行过多高负载 FFmpeg 进程。
- 是否有大量重复生成中间文件。
- 短预览是否可以使用较低分辨率。

只有输入文件编码、分辨率、时间基等兼容时才能使用安全的 stream copy。

无法直接拼接时，使用规范化转码，保证结果正确性优先。

# 八、第六阶段：前后端完整工作流联动

## 8.1 目标流程

用户实际操作过程应当是：

**01 创意需求**

输入项目名称、目标和要求，通过真实 LLM 生成创意分析结果。

**02 分镜与概念图**

确认和编辑分镜，使用真实 AI 图片模型生成关键帧图片。

**03 AI 视频生成**

针对分镜生成真实视频，确认使用哪个视频版本。

**04 配音与素材**

生成真实旁白，添加背景音乐、音效和字幕，在时间线上完成编排。

**05 单镜头调试（可选）**

选择镜头进行真实 FFmpeg 精修，并决定是否采用精修版本。

**06 最终导出**

读取完整时间线，合成有声音、有画面、可选字幕的 MP4 成片，并允许下载素材 ZIP。

## 8.2 工作流状态管理

当前 `state.stepsCompleted` 不能单独成为业务完成状态的可信来源。

需要由后端真实数据派生。

例如：

- 01：项目存在有效创意及分镜结果。
- 02：存在已确认的分镜与所需图片。
- 03：存在选定的视频素材。
- 04：时间线已保存且必要素材可用。
- 05：可选，无须强制完成。
- 06：最终输出文件已验证并保存。

配音不是所有视频的必需条件。

用户可以选择无配音、无背景音乐、只保留原视频音频。

第 04 步应根据“时间线准备就绪”判断是否能够继续，而不是简单判断是否存在任意 `audio_asset_id`。

第 05 步可以跳过。

如果用户在第 06 步发现问题，应允许返回第 04 或第 05 步修改后重新合成，不必重新调用昂贵的图片与视频生成 API。

## 8.3 项目一致性

所有流程状态应绑定：

- 当前真实用户 ID。
- 当前创意项目 ID。
- 分镜 ID。
- 素材 ID。
- 任务 ID。
- 时间线版本。

切换项目时要清理旧项目的临时 UI 状态，避免跨项目显示错误素材。

页面刷新后应恢复已有工作流。

不得使用其他项目的缓存状态代替当前项目真实数据。

# 十、测试与验收

## 10.1 工作流集成测试

创建一个包含 3 个分镜的真实测试项目。

准备：

- 3 个真实视频文件。
- 2 段真实旁白。
- 1 段背景音乐。
- 1 个短音效。
- 3 段字幕。

完成以下测试：

1. 进入第 04 步。
2. 为指定分镜生成配音。
3. 试听生成的 WAV。
4. 调整配音音量。
5. 添加背景音乐。
6. 在时间线调整音效位置。
7. 保存时间线。
8. 刷新页面并确认时间线恢复。
9. 进入第 05 步选择一个分镜。
10. 调整亮度及饱和度。
11. 生成精修视频。
12. 选择精修版本用于最终成片。
13. 进入第 06 步。
14. 合成 MP4。
15. 播放完整视频。
16. 验证背景音乐与旁白真实存在。
17. 验证字幕时间。
18. 下载 MP4。
19. 下载 ZIP。
20. 重新登录后查看已生成成片。

此测试可以使用已经存在的真实素材，不必每次都重新调用付费 AI 视频模型。

## 10.2 视频质量验收

通过 FFprobe 或相应工具验证：

- 视频文件可正常打开。
- 实际视频时长合理。
- 有视频轨。
- 配置了音频时必须有音频轨。
- 视频分辨率与导出配置一致。
- 帧率符合预期。
- 视频片段顺序正确。
- 配音时间位置正确。
- 背景音乐真实混合。
- 不存在明显异常静音或双倍叠音。
- 字幕时间正常。
- 文件不为空且能完整解码。

不允许仅靠 FFmpeg 进程退出码为 0 判断成片合格。

## 10.3 性能测试

分别测试：

- 单个图片生成。
- 单个视频生成。
- 带参考图的视频生成。
- 2 个用户同时提交。
- 多个运行中视频任务轮询。
- 图片和视频混合提交。
- 视频生成结果下载。
- 三镜头视频合成。

记录优化前后数据。

重点展示：

- 平均耗时。
- 中位数。
- P95 耗时。
- 队列等待时间。
- Provider 运行时间。
- 文件下载时间。
- 任务失败率。
- Worker CPU、内存和磁盘占用。

对比时保持模型、时长、分辨率和样本条件尽量一致。

如果生成时间主要受服务商影响，应如实说明代码优化无法显著改变其推理时间。

## 10.4 安全与回归测试

必须验证：

- 普通用户不能操作他人素材。
- 不能通过伪造 asset_id 获取他人私有视频。
- 未登录不能提交合成任务。
- 不存在任意服务器文件访问。
- 非法音频上传被拒绝。
- FFmpeg 参数无法被注入。
- 同一任务不会重复执行。
- 任务异常不会覆盖原始文件。
- 第 01～03 步的真实生成功能没有退化。
- 登录注册及 API Key 配置没有受到破坏。

# 十一、实施顺序

请按以下四个开发批次执行，避免大量功能同时改动。

## 批次 A：真实配音和音频素材

完成 Piper 音色映射、单分镜配音、试听、上传音乐和音效、字幕文件修复。

## 批次 B：时间线和最终 MP4 合成

完成视频轨、配音轨、音乐轨、音效轨和字幕轨的真实合成。

这是最高优先级的业务闭环。

## 批次 C：单镜头精修与完整导出

实现真实视频对比、滤镜精修、版本选择及最终成片关联。

完善 MP4 播放和 ZIP 打包。

## 批次 D：性能优化与全面测试

先建立耗时监测，再调整 Worker、网络连接、任务轮询、下载和前端渲染。

运行完整回归测试，并进行最终部署验证。

如果工作量较大，优先确保批次 A、B、C 能输出真正可播放的完整视频，不要将主要精力花在复杂监控平台的 UI 设计上。

# 十三、最终成功标准

本次开发完成后，AIGV Studio 应当能够：

用户通过 LLM 完成创意分析，使用图片模型制作关键帧，通过视频模型生成多个分镜视频，然后在第 04 步配置真实配音、背景音乐、音效和字幕，在可编辑时间线上完成编排，按需进入第 05 步优化指定镜头，最后在第 06 步合成一个可播放、可下载、包含真实音视频内容的 MP4 文件。

完成视频创作的整个流程中，除调用真实 AI 模型外，不应再依赖伪造数据、模拟音频、占位视频和仅存在于前端的时间线。
