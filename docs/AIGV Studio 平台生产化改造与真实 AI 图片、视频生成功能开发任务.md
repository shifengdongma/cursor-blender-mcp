# 三、第一阶段：完善真实登录注册与账户认证系统

## 3.1 总体目标

实现真正可用的账户系统。

所有核心业务页面和生成 API 必须要求登录。用户注册以后能够通过真实数据库完成身份验证，退出登录后不能继续操作受保护资源。

不得只依赖前端 JavaScript 判断是否登录。

## 3.2 统一用户认证数据

建议首期继续使用现有 SQLite，避免为了基础认证改造而迁移整个数据库。

对当前 `auth_users` 表进行兼容性扩展，必要字段包括：

| 字段 | 功能 |
|---|---|
| id | 用户唯一 ID |
| username | 登录用户名 |
| email | 邮箱 |
| password_hash | 安全密码哈希 |
| nickname | 用户昵称 |
| avatar_path | 头像路径 |
| role | 平台角色：admin/user |
| status | active/disabled |
| is_active | 如保留现有字段，须与 status 统一语义 |
| created_at | 注册时间 |
| updated_at | 最后修改时间 |
| last_login_at | 最后登录时间 |
| failed_login_count | 连续登录失败次数 |
| locked_until | 临时锁定截止时间 |
| session_version | 会话失效控制版本 |

如果现有数据表具有其他已经使用的字段，必须保留。

用户名设置数据库唯一约束，并检查现有数据中是否存在重复值。

对于 `users` 和 `project_memberships`，继续保留其租户及项目管理职能，通过稳定的外键或映射关系关联实际登录账户。

明确区分：

- 平台角色：`admin`、`user`
- 项目成员角色：`owner`、`editor` 等

项目 owner 不自动拥有全平台管理员权限。平台管理员权限不得通过客户端提交字段、项目成员身份或演示用户选择获得。

建立数据库迁移脚本，兼容当前存量用户，禁止直接删除原有用户数据。

对 `users.json` 进行一次性迁移和备份，迁移成功后不再允许旧 JSON 成为绕过 SQLite 账户状态或密码校验的认证来源。

## 3.3 完善注册功能

注册页面沿用现有布局，新增或完善如下字段：

- 用户名
- 昵称
- 邮箱（可选）
- 密码
- 确认密码
- 用户协议确认

要求：

1. 用户名长度与字符类型必须校验，禁止空白用户名。
2. 密码建议至少 8 位，并限制过长输入。
3. 两次密码必须一致。
4. 邮箱填写时必须验证格式，唯一性规则由后端统一执行。
5. 密码使用 Werkzeug 支持的安全密码哈希方案，不允许明文存储。
6. 用户名冲突返回 HTTP 409。
7. 所有新注册账号默认 `role=user`。
8. 不允许在注册请求中指定 `role=admin`。
9. 注册时间从服务器真实 UTC 时间生成。
10. 成功后可以自动建立登录 Session，但必须执行真实会话初始化。
11. 注册失败必须返回明确且安全的错误信息。
12. 注册过程必须使用数据库事务，保证不会出现只写入部分账户数据的情况。

可以按当前业务需要决定是否开放公众注册，并为管理员预留关闭公开注册的配置项。

邮箱验证属于可选扩展。如果没有配置邮件发送服务，不得将未验证邮箱展示为已验证。

## 3.4 完善登录功能

使用现有 Flask Session 体系作为基础，不必为了普通 Web 登录强制引入 JWT。

要求：

1. 通过数据库查询真实用户。
2. 校验密码哈希。
3. 检查用户是否被禁用或临时锁定。
4. 登录成功后重新生成有效会话及 CSRF Token。
5. Session 只保存必要身份标识，不保存密码及完整敏感用户数据。
6. 后端后续请求重新读取当前用户的角色、状态及会话版本。
7. 用户修改密码、管理员禁用账户或重置会话版本后，旧会话应失效。
8. 登录成功更新最后登录时间。
9. 登录失败增加失败次数，支持合理的限流和临时锁定。
10. 处理账号不存在、密码错误和服务异常等情况。
11. 所有密码和密钥不得写入日志。

登录页支持登录成功后返回原先尝试访问的系统页面，但必须防止开放重定向漏洞。

## 3.5 完成全站登录保护

重点修改：

`app.py`、`auth_middleware.py`、`control_plane_routes.py`、`creative_routes.py` 及其他业务路由。

需要逐项审计所有 Flask Route，包括：

- 主工作台
- 创意生产工作台
- 算力平台
- 云主机管理
- 资产管理
- 项目管理
- Prompt 管理
- 分镜管理
- 图片与视频生成
- 任务状态与生成历史
- 用户素材和文件下载
- 管理员管理接口

明确公开路由白名单。

原则上只有登录、注册、必要的静态资源、安全处理后的健康检查，以及用于初始化登录表单的 CSRF 接口可以匿名访问。

未登录访问受保护 HTML 页面时，重定向到 `/login`。

未登录访问受保护 API 时，返回 HTTP 401 和统一 JSON 错误结构，而不是返回 HTML 登录页。

用户已登录但权限不足时返回 HTTP 403。

**特别要求：禁止通过直接输入 `/creative-studio`、`/compute-platform`、`/api/jobs` 等地址绕过登录。**

不得只在前端隐藏页面或按钮。

对于 `/web/<filename>` 等静态文件入口，应保持必要 JS/CSS 可访问，但不能通过静态目录暴露用户上传文件、数据库、环境变量、任务私有结果或后台敏感配置。

## 3.6 CSRF 和 Cookie 安全

复用并完善 `backend/csrf.py`。

要求：

- 对 Cookie Session 下的状态变更请求实施 CSRF 保护。
- 为前端提供安全的 CSRF Token 获取机制。
- 所有需要保护的 POST、PUT、PATCH、DELETE 请求统一携带 Token。
- 对登录、注册接口采用适合未认证用户的 CSRF 保护方式。
- 配置 HttpOnly、SameSite 和生产 HTTPS 下的 Secure Cookie。
- 用户退出登录后清除会话。
- 生产环境禁止使用临时随机 SECRET_KEY 作为每次启动的新密钥。
- 不允许通过关闭 CSRF 来解决前端请求失败。

请为前端抽取统一的 API 请求函数，避免多个 JS 文件重复实现 Session、CSRF 和错误处理。

## 3.7 第一阶段测试

至少覆盖：

- 正常注册、重复注册和非法注册。
- 正确密码、错误密码、禁用用户登录。
- 未登录访问业务页面和 API。
- 登录后访问正常业务页面。
- 退出登录后的访问拒绝。
- 修改密码后的旧会话失效。
- CSRF Token 缺失或错误。
- 伪造 Session、修改本地存储、修改请求参数无法越权。
- 原有用户迁移后的密码验证。

# 五、第三阶段：真实 AI 图片与视频生成 API 集成

这是本次开发最重要的核心任务。

## 5.1 总体目标

将当前的展示型图片、视频生成工作流改造为：

用户输入 Prompt → 选择模型及参数 → 创建真实生成任务 → 后端调用第三方 API → 查询任务状态 → 获取生成结果 → 保存文件 → 前端预览和下载 → 历史记录保存。

必须与真实注册用户及其项目关联。

### 5.2 推荐接入策略

首期以国内云端 API 为主，避免强依赖个人开发者自行部署高成本 GPU。

优先尝试：

**图片：** 火山方舟 Seedream，备用阿里云百炼万相。

## 5.4 实现真实 AI 图片生成

在现有创意工作台图片生成流程中实现以下功能。

### 前端配置

允许用户选择：

- 图片生成模型
- Prompt
- 反向提示词（仅适用于支持该能力的模型）
- 图片比例
- 图片尺寸或分辨率档位
- 图片数量
- 随机种子（适用时）
- 参考图片（图生图模式）

默认只显示真实已配置、已验证可用的模型。

不支持某个参数的模型，前端隐藏或禁用对应配置。

### 文生图

流程：

1. 用户填写 Prompt。
2. 前端校验参数。
3. 向后端提交生成请求。
4. 后端验证当前账户及额度限制。
5. 验证模型及参数是否合法。
6. 创建数据库任务。
7. 调用真实图片生成 API。
8. 保存任务状态。
9. 获取返回的图片文件或图片 URL。
10. 将生成结果保存到本地受控存储或对象存储。
11. 创建用户素材记录。
12. 前端展示结果。

图片生成完成后应支持预览、下载、重新生成、复制 Prompt、查看生成参数。

### 图生图

使用用户上传的参考图片进行生成。

必须：

- 服务端验证图片格式及大小。
- 检查当前用户对参考图片是否有访问权限。
- 按 API 要求转换上传格式或图片 URL。
- 支持将生成结果关联原始参考图。

不允许使用用户上传文件路径直接访问服务器任意位置。

### 多图片生成

如提供“生成 4 张”等选项，必须确保其含义与实际 API 能力一致。

若 Provider 不支持单次多图，可创建多项子任务，但应正确统计调用次数和费用。

失败或超时必须显示真实错误状态。

不能使用随机图库图片替代生成结果。

## 5.5 实现真实 AI 视频生成

支持以下两类核心功能。

### 文生视频

用户输入：

- 视频 Prompt
- 模型
- 画面比例
- 视频时长
- 分辨率
- 其他模型支持的参数

前端可以观察：

- 排队中
- 已提交
- 生成中
- 已完成
- 生成失败

若第三方未提供精确进度百分比，则只显示阶段状态和运行时长，不允许模拟真实百分比。

### 图生视频

用户可以选择：

- 已生成的图片
- 当前项目中的图片素材
- 自行上传的图片

将图片作为参考素材，提交视频生成任务。

生成结果必须与原始图片和所属项目关联。

### 视频结果

成功生成后：

- 使用真实 MP4 或其他实际支持的格式播放。
- 支持视频预览。
- 支持下载。
- 展示真实生成模型和参数。
- 保存真实创建及完成时间。
- 展示失败原因。
- 支持查看生成记录。
- 支持从已保存图片继续创建视频。

如果第三方提供的是临时签名 URL，应及时由可信后端下载到持久化存储；不能长期将即将失效的 URL 当作永久素材地址。

下载过程需要验证来源域名、文件类型及大小，防止 SSRF、恶意跳转及磁盘耗尽。

## 7.2 重点安全检查

需要执行完整的安全自查：

**身份认证：** 未登录不能访问业务资源，禁用账户不能继续使用，修改角色后旧权限不能保留。

**对象权限：** 用户 A 不能修改、查看或删除用户 B 的私有项目、分镜、任务、素材。

**文件安全：** 避免目录穿越、任意文件上传、任意本地文件下载和危险文件类型处理。

**API Key：** 仅服务端保存，不进入公开 API 响应。

**生成成本：** 设置每用户并发上限、频率限制及管理员可配置的成本保护。首期不需要完整支付系统，但必须避免未授权的无限量计费调用。

**管理接口：** 所有管理员操作经过数据库中的真实角色校验。

**Session：** 确保修改密码、角色降级和禁用账户能够使旧会话失效。

**部署：** 生产环境需要 HTTPS，建议使用 Nginx 反向代理及正式域名。当前 HTTP IP 地址仅适合受控测试，不应作为安全账户系统的最终公开部署方式。

不要因为本次重点是图片和视频生成，就破坏其他模块。

## 7.4 部署改造

保持适合个人开发与单台云服务器部署的结构。

推荐首期架构：

```text
Browser
   |
   v
Nginx / HTTPS
   |
   v
Flask + Gunicorn
   |
   +---- SQLite（初期）
   |
   +---- 本地资产目录
   |
   +---- 独立任务 Worker
   |        |
   |        +---- AI Image API
   |        |
   |        +---- AI Video API
   |
   +---- Blender（可选）
```

对于生产访问量增长的情况，可以预留未来迁移 PostgreSQL、Redis 和对象存储的空间，但这些不作为首期开发的强制条件。

### 部署要求

1. 检查当前实际服务器环境和 Python 版本。
2. 更新 `requirements.txt` 并锁定兼容依赖。
3. 提供数据库备份与迁移脚本。
4. 提供正式环境变量模板。
5. 通过环境变量配置 API Key。
6. 确保 Gunicorn 多 Worker 不会重复启动后台任务线程。
7. 建议将生成 Worker 独立于 Web 进程运行。
8. 实现任务异常恢复。
9. 为日志设置大小限制或轮转。
10. 为生成文件设置存储路径和容量控制。
11. 提供启动、停止、重启和查看日志命令。
12. 保证升级后原有数据不被覆盖或清空。

在修改真实服务器前，先备份数据库、运行时数据及配置文件。

不得在没有执行环境的情况下声称已经完成线上部署。

# 八、自动化测试与最终验收

必须为新功能补充自动化测试，优先沿用仓库已有的 pytest 测试体系。

## 8.1 认证测试

至少覆盖：

- 用户注册成功。
- 重复用户名注册失败。
- 非法邮箱和弱密码拒绝。
- 正确账号密码登录。
- 错误密码拒绝。
- 未登录访问 API 返回 401。
- 普通用户访问管理 API 返回 403。
- 管理员访问管理 API 成功。
- 用户退出登录。
- 旧会话失效。
- 禁用账户不能登录或继续访问。
- 修改密码后验证新旧密码行为。

## 8.2 权限测试

建立两个普通测试账户和一个管理员测试账户。

至少验证：

- 普通用户无法修改管理员角色。
- 普通用户无法访问其他用户的生成任务。
- 普通用户无法下载其他用户的私有作品。
- 管理员可以查看用户列表。
- 管理员可以禁用用户。
- 最后一个管理员不能被降级。
- 恶意修改 `user_id`、`tenant_id`、`project_id` 参数无法越权。

## 8.3 AI 生成测试

使用 Mock Provider 进行稳定的自动化测试，覆盖：

- 正常提交任务。
- Provider 未配置。
- 第三方返回错误。
- API 超时。
- 异步任务轮询。
- 任务状态更新。
- 生成结果保存。
- 文件下载。
- 任务失败后重新尝试。
- Worker 重启后的任务恢复。
- 同一任务避免重复提交及重复计费。

有实际 API Key 的环境中，再分别执行最小额度的真实文生图和文生视频测试。

## 8.4 前端交互测试

验证：

- 未登录访问工作台自动跳转。
- 登录成功后正确进入工作台。
- 用户头像和昵称显示正确。
- 个人信息修改后立即刷新。
- 管理员导航只在管理员身份下显示。
- 普通用户不能通过手工输入地址访问管理页面。
- 新注册用户能创建真实项目。
- 图片生成状态正常刷新。
- 视频生成结果能够播放及下载。
- 页面刷新后任务记录仍然存在。
- 演示模式关闭后数据不会混杂。

## 8.5 验收标准

只有满足以下条件才能将任务标记为已完成：

1. 真实用户注册及登录可用。
2. 未登录不能操作系统核心功能。
3. 管理员与普通用户权限隔离正确。
4. 个人中心能够保存真实用户信息。
5. 管理员能够查看和管理真实账户。

7. 视频生成接口能够真实执行，或明确说明因密钥缺失尚待真实验证。
8. 生成任务可持久化，页面刷新不会丢失。
9. 图片与视频结果保存并关联正确用户。
10. 生产模式不出现伪造的用户、GPU 指标和任务记录。
11. 原有关键功能通过回归测试。
12. 提供完整测试报告及部署文档。
